## 方案与接口兼容

1. 保留每小时的 legacy 新队列发现。每次读取缓存时，以 pipeline 检查候选队列的 ready、retry、dlq、delay、默认 processing、历史索引及已知 Worker processing 键。只有已知存储键全部消失时，统一补查一次专属 processing，只核实缺失的已有候选，防止 ready 转移后误删真实队列。缓存校验不写入 Redis；注册表中的空队列保持现有语义。
2. search_tasks_page 的响应新增可空字段 exact_task_id。仅在第一页且 search 非空时按去除首尾空白后的字符串读取已有任务记录；确实存在且 ID 一致才返回 ID，否则为 null。它不改变 tasks、游标、扫描预算和筛选条件。
3. exact_task_id 用于任务页的直接 ID 定位，与原先自动详情请求一样独立于队列/状态/时间筛选；即使记录不在本页、没有历史索引或被其他筛选排除，精确 ID 定位仍可用。该字段仅返回 ID，不重复传输完整详情；旧调用方可忽略它。
4. 前端从已完成的列表查询读取精确命中，仅对当前查询、每个搜索词自动打开一次。普通词、无效 ID 和过期响应均不得打开抽屉；轮询和关闭抽屉不得自动重新打开。

比较：缩短全局扫描间隔会增加 Redis 扫描负担；UUID 正则会遗漏旧 ID；额外添加显式搜索模式会扩大交互范围。因此选择候选缓存校验及列表响应确认精确命中。

## 自查、风险与回滚

- 实施前复核：不能仅检查 ready 键，否则处理中的旧消息会误消失；不能只记最初发现键，否则状态转移会回归；需要保留动态 processing 的兜底发现。
- 精确定位必须在服务端确认，并与分页响应绑定；不能直接根据未完成查询中的 search 打开详情。自动刷新不得重复打开已关闭抽屉。
- Redis 查询与外部删除不是跨请求快照；验收保证删除完成后的下一次查询，不能保证查询过程中并发写入的瞬时强一致性。
- 已知键全部失效时的专属 processing 补查可能扫描键空间，但不会把普通缓存命中改成全局扫描。批量失效只执行一次 processing 扫描，避免每个删除队列分别扫描；新出现的未注册旧队列仍沿用原有每小时发现窗口。
- 回滚时仅撤销本次代码和构建产物；本次校验与搜索不迁移/删除业务数据，无数据回滚步骤。保留用户原有改动及追加式 KI 历史。
