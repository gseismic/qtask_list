# Dashboard 体验与操作修复设计

- 日期：2026-10-16
- 基线：`d09441a`，工作树干净。
- 输入：本轮界面评审确认的 11 项缺陷，以及总览筛选、采样保留、新任务跳转三项优化。
- 原则：采用 `ux-philo-zh` 的真实场景与持续价值原则、`api-design-zh` 的风险显式与契约一致原则；React 实施参考 `vercel-react-best-practices`。

## 用户与场景

沿用已有文档中维护 30～100+ 队列、多个 namespace 的管理员假设，频率为定性排序。

| 场景 | 优先级 | 完成条件 |
| --- | --- | --- |
| 常开巡检，查看积压、完成速率与异常 | 高 | 所示更新时间对应当前数据；空闲后新任务不误报停滞。 |
| 从 DLQ 或 task_id 追查失败原因 | 高 | 显示最新状态、错误原因与下次执行时间，操作符合最新状态。 |
| 修复后重放，核对新任务结果 | 高 | 失败/跳过/取消任务可按需更新截止；成功后可直接打开新任务和血缘。 |
| 持续筛选、翻页查找任务 | 高 | 旧响应不能污染新查询；翻页期间列表稳定。 |
| 恢复特定失联 Worker | 中但高风险 | 确认范围与实际恢复范围完全一致，保留心跳复核。 |
| 确认告警、清空与删除 | 中 | 当前弹窗内反馈失败，告警确认立即生效。 |
| 分屏巡检与跨页面返回 | 中 | 异常列可见，筛选与采样不因 SPA 导航丢失。 |

## 方案比较与定稿

### 刷新与分页

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| 所有页面各自保持现有轮询 | 改动少 | 更新时间、停止开关与刷新范围仍不一致。 |
| 所有数据都塞进全局快照 | 只有一个刷新来源 | 大任务列表增加全局请求成本，翻页与实时更新互相干扰。 |
| 统一刷新信号与间隔，列表拥有查询状态 | 高频控制一致，查询可隔离，翻页可稳定 | 需要公共分页请求钩子与明确的暂停反馈。 |

采用第三种。顶栏刷新触发当前任务列表和详情更新；任务列表默认实时刷新第一页，翻页时取消该列表的自动刷新并说明原因，用户可手动回到最新第一页。分页、筛选、刷新、卸载通过查询代次与请求序号隔离；保留后台更新失败前的数据和该数据的更新时间。

### Worker 恢复范围

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| 把行按钮改为“恢复整个队列” | 后端无需扩展 | 无法表达管理员只恢复一台失联机器的意图。 |
| 增加独立单 Worker API | 语义明确 | 重复现有恢复协议与实现。 |
| 既有恢复 API 增加可选 `worker_id` | 兼容现有调用，支持精确范围，复用原子心跳复核 | 需要校验 worker_id 并补范围测试。 |

采用第三种。`QueueAdmin.recover(..., worker_id=None)` 保持旧队列级默认行为；指定 worker_id 时只检查与恢复该 Worker 的 processing，不触及其他 Worker 或 legacy processing。Worker 行必须传 worker_id。不得将该标识解释为 Redis glob；按既有标识约束校验，并使用精确 key。

### 详情操作与重放

最新记录的 outcome、location、delay_reason 与 deadline 决定状态；列表提示仅用于缺少字段的旧记录。completed 不属于后端 replay 契约，因此不显示重放按钮。failed/skipped/cancelled 的截止时间已过时，在确认弹窗内填写新时间并调用普通 replay；仍在待处理容器中的过期任务使用专用 requeue-expired。两者不得混用。

复用确认弹窗并把错误和输入放进当前操作上下文；成功显示新 task_id 和“查看新任务”，血缘支持跳转。保留旧 DLQ 的重入队路径；没有可还原 payload descriptor 的旧记录不提供必然失败的 V2 replay。

### 监控与总览

在应用层保留浏览器采样，SPA 导航不清空。停滞计时仅覆盖连续存在 ready 积压且有在线 Worker 的观测区间，完成、空闲、无 Worker、长观测中断均重置。旧指标未回填时显示未知。

不增加缺少调度器输入的批次模型。主图改为当前待处理的状态构成，分别表达排队、执行、延迟和旧 retry；完成增量单列显示并标明浏览器观测窗口。这样各段来自同一时点、同一分母，用户无需理解“观测完成与当前剩余参考比”。

总览增加 namespace 与队列名筛选，保存折叠选择；健康 namespace 默认收起，有异常的组默认展开。队列页沿用操作卡片，服务逐队列管理。窄窗口通过滚动或调整布局完整呈现异常列；状态筛选不同时重复占用 tabs 和下拉框。

### 告警确认

沿用本浏览器存储边界，通过应用层操作立即重算告警，跨标签页 storage 变动也更新。不再先输出已恢复告警再清理。持续故障被确认后保持确认；监测到恢复再复发时重新提示。存储失败应在当前页面反馈，不能伪装写入成功。

## 三轮查漏补缺

1. **正常任务闭环**：第一页自动刷新、翻页稳定、单 Worker 精确恢复、失败详情、过期终态重放、新任务与血缘跳转；全部对应可执行的 API 与字段。
2. **故障与竞争边界**：API 失败的旧数据时间、确认弹窗内错误、重复点击、旧分页响应、请求卸载、恢复时心跳重新出现、localStorage 写入失败；任何失败不得扩大范围或显示虚假的成功。
3. **兼容与规模**：保留队列级恢复参数与返回结构、legacy DLQ 路径、现有 V2 重放限制；100+ 队列只在全局成功快照中统一采样，避免每页重复观测；1024px 及更窄布局需完整访问异常信息。
