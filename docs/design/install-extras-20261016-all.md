# 安装 extras 设计：增加 all 组

- 日期：2026-10-16
- 状态：定稿
- 关联计划：`docs/dev/PLAN-023-all-extra.md`

## 背景与接口受众

安装 extras 是项目面向使用者的包管理接口。项目当前提供 `dev`、`dashboard`、
`storage` 三组可选依赖，用户可以组合使用，但需要记住并列出每一组。增加 `all` 后，
用户可以运行 `pip install -e ".[all]"` 一次安装基础依赖和所有可选依赖。

## 方案比较

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A：显式组合 | 保持现状，使用 `pip install -e ".[dev,dashboard,storage]"` | 不增加元数据，也没有依赖清单重复 | 使用者必须了解并记住全部 extras |
| B：聚合 all | 新增 `all`，列出所有可选依赖的去重并集 | 命令简短；含义直接；可继续单独选择某个 extra | 清单与各子组有重复维护成本；包含开发工具 |
| C：只聚合运行时 extras | 新增 `all`，只包含 Dashboard 和 Storage 依赖 | 用于运行部署时不会安装测试和静态检查工具 | `all` 没有覆盖所有可选依赖，语义容易误解；开发者仍需额外组合 `dev` |

## 定稿

采用方案 B。`all` 表示安装项目声明的全部可选依赖，包含 `dev`、`dashboard` 和
`storage` 的依赖；基础依赖由 pip 在安装项目时照常安装。`all` 中每个依赖只列一次，
并沿用对应分组的版本下限。README 安装说明要明确 `all` 包含开发工具，避免使用者
误以为它只是运行时组件集合。

清单需要在新增或修改任一子组依赖时同步检查。当前 pyproject 静态 extras 没有可靠的
组内引用机制可避免这个维护点；把子组名写成自身发行包依赖会引入自依赖，不采用该做法。

## 三轮查漏补缺

1. **语义检查**：确认 `all` 指全部 optional dependencies，而基础依赖并非 optional，
   仍通过常规项目安装自动引入。
2. **范围检查**：确认开发依赖属于可选组，因此纳入 `all`；同时在 README 明示包含
   pytest、ruff、mypy 等工具，避免部署用户误选。
3. **一致性检查**：将 `all` 定义为三个现有组的依赖去重并集，逐项核对版本下限；
   README 中提供对应命令，并把后续子组变更时检查聚合列表作为维护约定。

## 验收条件

- `pyproject.toml` 声明 `all` extra，涵盖现有三个可选组且不重复列同一依赖。
- README 提供 `pip install -e ".[all]"` 示例并说明它包含开发依赖。
