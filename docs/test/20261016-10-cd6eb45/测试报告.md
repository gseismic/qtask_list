## 对参考截图的解读

参考图显示“未处理 (4) / 已处理 (1)”，画面中的四条都是无人消费告警；当前 Redis 还存在 `dashdemo:fetch` 的一条 DLQ，因此隔离浏览器会显示“未处理 (5) / 已处理 (0)”。告警确认状态保存在浏览器本地 `localStorage`，不会跟随 Redis 或其他浏览器会话同步。结合当前数据，参考图中那条已处理记录很可能就是 `dashdemo:fetch` 的 DLQ 告警；这是根据计数差异作出的推断，无法从独立测试会话读取原浏览器的本地状态来确认。

参考图本身没有展示 DLQ 卡片，所以仅凭原图不能判断 DLQ 链接落点。本次从当前告警页实际点击了 DLQ 卡片并验证了目标队列和状态。

## DLQ 详情 404 的数据证据

- DLQ 列表接口返回 200，死信消息仍在 `dashdemo:fetch:dlq`，消息信封包含 task id、`fetch_kline`、attempt 和失败原因。
- 任务详情接口返回 404；Redis 中 `qtask:task:cf47941a-c541-4a4e-b917-5b993ee08cf0` 不存在，但 `qtask:hist:dashdemo:fetch` 的 ZSET 仍包含该 task id。
- 索引分数对应 2026-09-20 17:05（Asia/Shanghai），比本次测试早约 26 天；超过默认 15 天历史保留期。
- 当前实现规定仍在 DLQ 的任务记录不设置 TTL（[history.py](../../../qtask_list/history.py#L1)，[README.md](../../../README.md#L315)）。Dashboard 的单任务接口只从历史记录读取（[main.py](../../../qtask_list/dashboard/main.py#L415)，[admin.py](../../../qtask_list/admin.py#L519)）。

现有 Redis 数据与当前“DLQ 消息期间保留任务记录”的不变量不一致。时间和缺失的 Hash 符合旧版记录已过期或被旧流程清理的特征，但当前数据无法证明究竟是哪一种。建议后续处理旧 DLQ 记录兼容：详情缺失时由队列消息信封提供最小详情，或在迁移/巡检时报告孤儿 DLQ；不要把本次定位误判为错误队列。
